## 1. Context

V2 starts from the monorepo after the security-correctness SDD has shipped (`0.23.x`). At
`v0.22.1`, which this SDD read, `netray` is one binary that runs one process per subcommand; lens
grades a domain by calling five services over HTTP (`crates/lens/src/backends/`) and maps five
status vocabularies into its own; it builds every SSE event after the whole check
(`crates/lens/src/routes.rs`, `build_sse_events`); snapshots keep a summary for 30 days
(`crates/lens/src/snapshot/`); six SolidJS apps (each
`crates/*/frontend/package.json` depends on `solid-js`) and hand-written HTML under `site/`
make up the UI. The
security-correctness SDD fixes the SSRF paths, the email and IP scoring and the incomplete
semantics (SC12, SC14) that this design takes as given.

| S42 | A probe's close is the server's answer (operator, 2026-10-20; `v2-tls-probe-close`). A ClientHello probe whose connection ends by FIN or RST after the ClientHello was written, with no byte received, is `refused` with the answer `closed` or `closed (reset)`, not unanswered. This is not a failed lookup: the handshake on the same address and port just succeeded, so the server speaks TLS there; it was sent a well-formed offer and ended the connection instead of answering it, as an alert does; S34 already counts a reset as an answer. Windows SChannel refuses disabled versions this way. The probe cannot tell a close after reading the offer from a close at accept: a server that drops connections over a per-client connection limit reads as refusing (accepted residual, `v2-tls-probe-close` decision log). A timeout, bytes that decide nothing before the close (a partial record, a warning alert), garbage, an alert other than a fatal handshake_failure, protocol_version or insufficient_security, and a failure before the ClientHello was written (connect, STARTTLS, the write) stay unanswered. A stated grade change: such servers move `tls.legacy_versions` and `tls.weak_suites` from `unmeasured` to a verdict, and their TLS section from incomplete to scored. Refines S34 and S41. |

Dependency direction: modules → `engine` → `model`, modules → `model`; the binary depends on all
and builds the registry. The edge never points from `engine` to a module. The
engine never names a module crate (P40); the binary registers them. `web` names module crates
only for inspector jobs, which have no domain verdict and no common shape (a DNS query, a TLS
host:port, a URL, an IP).

### 3.2 One domain run

1. **Boundary.** `web` parses the domain once (IDNA: UTS #46 to the A-label, which is the form
   stored and shown, v2-input-edges; public suffix sanity) into a `Domain`; nothing behind it takes a raw string. A cached complete run inside the cache window answers directly; "re-check now" bypasses it under the per-domain throttle (R14).
2. **Resolve stage.** The engine resolves the facts several modules need — A, AAAA, MX, CAA — once, into `Facts`. Today every backend resolves on its own: lens's wave 1 starts DNS, TLS, HTTP and email concurrently (`crates/lens/src/check.rs:56-129`) and only the IP backend receives DNS's addresses. With `Facts`, CAA lives in DNS evidence and TLS references it (R4, R29).
3. **Sections.** Every registered module runs concurrently on `Facts`, each under its section deadline inside the hard deadline (SC8). Each finished section — checks plus evidence — is sent on a bounded channel as it completes; `web` turns it into HTML fragments for the stream (R22, S25).
4. **Grade.** When every section has finished or timed out, the engine scores once with the current profile version (R5, R6). Any errored, timed-out or unmeasured weighted section makes the run `Incomplete` (R8, SC12, SC14).
5. **Record.** A complete run goes to the store: identical to the latest entry (R10) → only last seen moves; otherwise the run and its diff against the predecessor are stored. An incomplete run is diffed against the last complete one and not stored.
6. **Close.** Grade and diff are the stream's last fragments. `/r/<id>`, evidence views, badge, OG card and the API read the same stored run; none computes a verdict (R5, R47).

### 3.5 Check model (`netray-model`; R1–R3, R8, R37)

A check has two halves: what never changes between runs lives in the **catalogue**, what a run
measured lives in the **result**.

**Catalogue entry** (`CheckSpec`), one per check ID, all in one file (`checks.toml`, P36), which also
generates the compare page's own column (R46), the guide links and the fix copy:

| Field | Type | Note |
|---|---|---|
| `id` | `CheckId` | `<protocol>.<name>`, each part `[a-z][a-z0-9_]*` (operator, 2026-10-09), e.g. `tls.chain_trusted`; unique across the result (R1); never reused once released |
| `protocol` | `Protocol` | `dns`, `tls`, `http`, `email`, `ip` |
| `title`, `finding`, `impact`, `fix_hint` | text | the four things of R37, the finding and the fix in plain sentences (R20) |
| `fix_owner` | `FixOwner` | one primary owner: `dns_provider`, `registrar`, `certificate_provider`, `web_server`, `mail_provider`, `hosting`. V1's `fix_for` returns 14 free-text variants (`crates/lens/src/routes.rs:109`), some naming two owners; R21's grouping needs one. Each value has one fixed label (operator, 2026-10-10), capitalised because the result page sets it as a group heading, as the board does: "Your DNS provider", "Your registrar", "Your certificate provider", "Your web server configuration", "Your mail provider", "Your hosting provider" |
| `severity` | `Severity` | `critical`, `high`, `medium`, `low`; static per check, derived from the profile: a hard fail is `critical`, weight ≥ 5 `high`, 3–4 `medium`, ≤ 2 `low` (stated in the header of `crates/engine/catalogue/checks.toml`) |
| `source` | text | RFC or specification section (R37) |
| `guide` | path | the guide page |

**Result** (`CheckResult`), one per check per run:

| Field | Type | Note |
|---|---|---|
| `id` | `CheckId` | must be in the catalogue and in the profile; a module emitting an unknown ID fails its contract test |
| `status` | `Status` | one vocabulary (R2): `pass`, `warn`, `fail`, `not_applicable` (by design, with reason), `not_tested` (every address failed locally, R8), `unmeasured` (error or timeout) |
| `findings` | list of text | what the module saw, for non-passing checks and for notes on a pass (SC7's empty DKIM `p=` is a note on a pass, not a status) |
| `evidence` | list of `EvidenceRef` | the blocks the status relies on, in this or another module (R4, R28) |

A stored check carries its findings and evidence references outside the fingerprint and the diff.

V1's extra words map once: `NotFound` → `fail`, `Skip` → `not_applicable`, beacon `Info` → a
finding on a `pass`. V1 `Skip` also stands for an error or a timeout (beacon's pipeline timeout,
`crates/beacon/src/checks/mod.rs:111`; tlsight's HSTS timeout, `crates/tlsight/src/quality/http.rs:133`, runs in
every TLS run but feeds no TLS check, so `http.hsts` in the HTTP module carries HSTS):
Phase 1a maps every `Skip` to `not_applicable`, so it stays equal to `0.23.x`; Phase 1b makes the
error and timeout cases `unmeasured` (S32, by Rule M, S34). Weight and hard-fail are not part of either half: they live in the profile
(§3.8).

**Several addresses.** TLS, HTTP and IP checks are measured per address. The check's status is the
worst over the addresses that were tested; addresses "not tested from here" are excluded; when all
are, the status is `not_tested`. Evidence keeps every address.

**Section and run.** A section is `measured` (its results), `not_applicable` (reason) or
`incomplete` (error, timeout, a weighted `unmeasured` check, or no weighted check measured — SC14).
A run is `complete` when no weighted section is `incomplete`; only then does it get a letter
(SC12), except F: a failed hard fail grades an incomplete run F, and the run is still not stored (S35).

### 3.6 Module trait (`netray-engine`; R4, R7, P40)

```rust
pub trait Module: Send + Sync {
    fn protocol(&self) -> Protocol;
    fn checks(&self) -> &'static [CheckId];          // what it may emit
    fn volatile(&self) -> &'static [EvidencePath];   // R10
    fn run<'a>(&'a self, ctx: &'a RunContext, facts: &'a Facts)
        -> BoxFuture<'a, SectionOutcome>;
}

pub trait FactsProvider: Send + Sync {               // implemented by netray-dns
    fn resolve<'a>(&'a self, ctx: &'a RunContext, domain: &'a Domain)
        -> BoxFuture<'a, Result<Facts, ResolveError>>;
}
```

- `RunContext` carries the deadline, the outbound fetch client from `netray-common` and the run's
  cancellation; a module never builds its own client (P18) or its own deadline (P12).

  module provides them through `FactsProvider`, so the engine depends on the trait, not the crate.
  A failed resolve makes every section that needs addresses `incomplete` (SC14), never N/A; a
  definite negative is S31.
- The engine owns the hard deadline and turns a module that overruns into `incomplete`; it keeps
  the sections that finished (SC8).
- Registration happens in the binary: `Registry::new(dns).with(tls).with(http).with(email).with(ip)`.
  Adding registration health (product strategy 7b) is a new crate plus one line here, the profile
  and the catalogue (P40).

### 3.7 Evidence (R7, R10, R27–R29)

Typed inside, generic when published (S15). A module computes with its own types (a certificate,
a parsed SPF record); what it stores, renders and serves is a projection into evidence blocks. A
block has an ID, a title and one of six shapes; the web layer renders each shape with one
component (R44, the evidence block), the API serves the same structure (R34), and one algorithm
diffs it (R12). No module ships templates.

| Shape | For |
|---|---|
| `records` | DNS resource records (owner, type, TTL, data) |
| `table` | typed columns and rows, one key column: addresses, cipher suites, headers, DNSBL answers |
| `chain` | ordered sequences: certificate chains, redirect hops |
| `tree` | nested structure: SPF includes, DNSSEC chain of trust, a DNS trace's delegation path |
| `fields` | key–value: a parsed DMARC or MTA-STS policy, certificate validity |
| `text` | raw bodies kept verbatim: an MTA-STS policy file, a BIMI SVG's metadata |

Rules that keep the shapes from growing into a UI language:

- **Closed and versioned.** The shape set carries one schema version; a new shape or a breaking
  change to one is an SDD decision, and every stored entry stays renderable for its lifetime
  (R11, R27: `/r/<id>` never changes).
- **Typed values, stable keys.** Values are `text`, `int`, `bool`, `time`, `duration`, `addr`;
  each module keeps a register of its field and column keys, and a released key is never reused
  with another meaning (the rule of check IDs). A later machine consumer (Guard, product strategy
  Phase 4) reads `tls.validity/not_after` as a time, not a string. The value types are closed, and
  there is no list type: a key with several values repeats in `fields` and `chain` items (`sans`
  N times), and a `table`'s key column holds unique values. A `time` is strict RFC 3339. A `records`
  entry carries tagged owner, type, ttl and data; `ttl` is an `int`. The register declares each
  block's shape as well as its keys and value types.
- **Data, never presentation.** A shape carries no colour, emphasis or collapse hint; emphasis is
  derived from the checks that reference the block (R28).

On the lens wire (S39), evidence is additive: `evidence: [...]` per section and `evidence: [block-ids]`
per check item. A typed value is tagged `{t, v}` with `t` one of the six value types. The
`tree` shape has no producer in Phase 1b. The lens summary carries `evidence_schema`
(`EVIDENCE_SCHEMA_VERSION = 1`). The V1 beacon stream gets one additive message, `type: "evidence"`, sent
before `summary`. Replay and production use the same path, the V1 email frontend ignores it, and the
existing beacon messages stay byte-identical (operator, 2026-10-13).

`validate` refuses five things: a block whose shape does not match its register, a duplicate block ID,
an unregistered block or key, a value of the wrong type, and a block whose ID carries another module's
prefix. A run also obeys one rule: a check with status `pass`, `warn` or `fail` references at least
one block, and every reference resolves in the same run. A check that is `not_applicable`,
`not_tested` or `unmeasured` may reference nothing (`v2-evidence` phase 1, monorepo 9e8f985).

Block IDs are stable and address-qualified (`tls.chain@192.0.2.1:443`, `dns.caa`). The grammar is
`<module>.<name>[@<qualifier>]`; the qualifier is an address, `address:port` or a port, and IPv6 is
bracketed. An ID is canonical: the qualifier is normalised on parse (an address in std Display form,
IPv6 lowercase and compressed; a port in strict decimal, 1–65535). A block lives once, in its natural module (R29: CAA in DNS); other modules' results reference it.
The resolve stage carries the blocks of the shared lookups (`dns.a`, `dns.aaaa`, `dns.mx`, `dns.caa`,
`dns.ns` and `dns.https`, with TTLs) in `Facts.blocks`. The DNS module also projects every record type
it got an answer for, those six included, and does not wait for the resolve stage: waiting cost up to
the resolve budget in latency, and a failed facts lookup alone made a DNS check `unmeasured`. When an ID
exists in both places, the section's block wins, so a DNS check always points at what it judged. Facts
blocks fill only the IDs no section carries, for example after a DNS timeout. A reference such as
`tls.caa_compliant` → `dns.caa` therefore resolves whenever the fact was answered. While resolver caches
diverge, it can point at DNS's view rather than the facts it was judged from; V1.5's single lookup
removes that. A records block keeps the highest TTL across resolvers (the rule of `dns.ttl`) and its
records in canonical order (owner, type, data); `dns.dnssec` also references the RRSIG, NSEC and NSEC3
blocks (operator, 2026-10-13, `v2-evidence` phase 2, A1 and A2). The block names and keys of
the `v2-evidence` spec (monorepo 8581575) are released keys.

One rule holds in every module: the block a judged check references contains the fact that decided
its verdict, and no value is invented. An unknown is omitted, never a zero or an empty placeholder;
the one exception is IP's absent text cells, which are deferred. lens drops a reference across modules
that does not resolve within the run (for example email → `dns.dnskey`). The `v2-evidence` phases 3–5
(monorepo 75b8ed9, A3–A5, operator 2026-10-13) refine the blocks:

### 3.8 Scoring profiles (R5, R6, R13)

- Profiles are files `profiles/v<N>.toml` in the engine crate, all embedded; `Profiles::get(n)`
  loads any of them, `Profiles::current()` the highest. Every stored run records its version, and a
  replayed run (R25) is scored with it.
- A released profile is never edited: a test holds each file's hash against a committed lock file
  (P35); a change is a new version, which the diff shows as a profile change (R13).
- Every check ID in the catalogue has a weight ≥ 1 in the current profile and vice versa (a test,
  P35/P36); the weight is the line height in the spectrum (R24). V1's unweighted checks
  (`score_section` ignores names missing from the profile, `crates/lens/src/scoring/engine.rs`)
  either get a weight or become findings.
- V2 starts at profile `v3` (V1's `crates/lens/profiles/default.toml` is `version = 2`). Runs from
  V1 are not in the history (S2), so `v2` need not be loadable by the engine.

### 3.9 Check catalogue v3 (R1, R4, R29; S12, S16)

The V2 catalogue, derived from what the crates emit at `v0.22.1` — the weighted names of
`crates/lens/profiles/default.toml`, tlsight's `crates/tlsight/src/quality/checks.rs`, spectra's
`crates/spectra/src/quality/checks.rs`, the lint categories of `crates/mhost-prism/src/api/check.rs:472-494`,
beacon's `crates/beacon/src/checks/*.rs` — and from the security-correctness SDD (SC5, R3.1,
R5.2), which V2 builds on. V1's 42 weighted checks become **54**: 10 DNS, 21 TLS, 12 HTTP,
10 email, 1 IP. Profile `v4` (S41) makes them **57**: 10 DNS, 23 TLS, 13 HTTP, 10 email, 1 IP.

**Rules.**

- Every check is emitted in every run, as `not_applicable` with a reason when it does not apply.
  Today tlsight emits no check at all when no address completes a handshake
  (`crates/tlsight/src/quality/mod.rs:34-38`) and its certificate and protocol checks only when
  that data exists; spectra's `redirect_limit` is emitted only when the
  limit is hit (`crates/spectra/src/quality/checks.rs:157`) and becomes a finding (S16). A
  conditional check would show up as added or removed in the diff (R12) without anything having
  changed.
- TLS checks are measured on every address, not on the first that answers (today
  `crates/tlsight/src/quality/mod.rs:32`, and lens reads only `ports[0]`,
  `crates/lens/src/backends/tls.rs:207`); the status is the worst over tested addresses (§3.5).
  The domain check inspects port 443; other ports belong to the TLS inspector.
- A check owns one fact; a check that needs another module's fact references its evidence block.

**DNS** (`netray-dns`, from `mhost-prism` and mhost 0.11 lints)

|---|---|
| `dns.dnssec`, `dns.dnskey_algorithm`, `dns.dnssec_rollover` | unchanged; DNSSEC lives only here (beacon's `dnssec` category ends) |
| `dns.caa` | owns the CAA records (evidence `dns.caa`) |

## 4. History and diff (R9–R16, R19)

First level: the store's shape, what counts as a change, how long things live, and how fresh
runs are admitted. `netray-store` owns all of it; the diff itself is the pure function in
`netray-model` (§3.1).

### 4.1 Schema (S2)

One table; a domain exists only through its entries. Types are portable (`TEXT`, `BIGINT`, no
SQLite-only functions); timestamps are Unix seconds.

| Column | Type | Note |
|---|---|---|
| `id` | `TEXT` PK | the `/r/<id>` short ID (nanoid, as `crates/lens/src/snapshot/shortid.rs` today) |
| `domain` | `TEXT` | the A-label form of the parsed `Domain` |
| `created_at` | `BIGINT` | when the entry was stored |
| `last_seen_at` | `BIGINT` | set at store, moved forward by every identical run (R11) |
| `predecessor_id` | `TEXT` NULL | the domain's previous entry; NULL for the first |
| `profile_version` | `BIGINT` | R6 |
| `grade` | `TEXT` | a letter; never `incomplete` (incomplete runs are not stored, R8) |
| `fingerprint` | `TEXT` | SHA-256 over the comparable content (§4.2) |
| `run` | `TEXT` | the full run as JSON: results and evidence (§3.5, §3.7), with the evidence schema version |
| `diff` | `TEXT` NULL | the diff against the predecessor, stored with the entry (R10) |
| `engine_version` | `TEXT` | the binary's version, for support |
| `duration_ms` | `BIGINT` NULL | how long the run took in milliseconds, stored with a new entry and left as it is by an identical run (the second migration); NULL for entries recorded before it |

Migrations are forward-only: once the second migration is applied, a binary that predates it refuses the database at start, so a rollback past it needs the database from before it.

Indexes on `(domain, created_at DESC)` and `predecessor_id`. Recording a run is one transaction
(P41): read the latest entry, compare, then update `last_seen_at` or insert. The one process (S1)
runs at most one run per domain at a time (§4.4); until §4.4 exists, and against any other caller,
the store serialises its own writes (record and sweep), so two records for a domain never race
(`v2-history`). The latest entry is the chain's head, the one no entry names as predecessor;
`created_at` and `last_seen_at` never move backwards, whatever clock the caller passes.

### 4.2 Identical runs (R10)

`fingerprint` hashes the canonical JSON of: the profile version; every check's ID and status;
every evidence block with the module's volatile paths removed and its sets in canonical order
(§3.7). Two runs are identical when the fingerprints are equal. An identical run moves the
latest entry's `last_seen_at` and stores nothing else; any other complete run becomes a new
entry with its diff.

An engine release that changes evidence without changing the domain (a new field, a new
canonical order) makes the next run of every domain a new entry whose diff shows evidence
changes. Such a release states it in its notes; the diff marks entries whose predecessor has
another `engine_version` (§4.3).

### 4.3 Diff (R12, R13, R19)

The diff compares the current run with the domain's latest stored entry (the last complete run):

- **Per check:** the R12 classes — fixed, improved, new, worse, now applicable, no longer
  applicable, added, removed, into or out of not tested — and into or out of not measured
  (`unmeasured`, Rule M). A not-tested or not-measured transition is never fixed or worse; when
  both sides are one of the two, the current status decides. A run lists every catalogue check of
  every section: a not-applicable section's checks as `not_applicable`, an incomplete or
  timed-out section's as `unmeasured`, so a domain gaining an address reads "now applicable" and a
  timeout "into not measured", never added or removed (`v2-history`).
- **Evidence:** per block, changed keys or rows without a status change, by the one generic
  algorithm over the six shapes (S15), only for sections measured in both runs; volatile paths
  are never reported.
- **Grade:** when the profile versions differ (R13), the grade change is split in two: the
  predecessor re-scored with the current profile (the profile's effect, possible because every
  version stays loadable, R6), then the current run against that (the domain's effect).
- **Release:** checks added or removed because the catalogue changed between engine versions are
  shown as such ("added by release", "removed by release"), not as changes of the domain; a check
  ID present in only one run is a release change exactly when the two `engine_version`s differ.

Without a stored predecessor the diff is replaced as R19 says. An incomplete run is diffed against
the last complete entry, shown with grade `incomplete`, and not stored.

### 4.4 Fresh runs, cache, re-check (R14)

- **The history is the cache.** A request for a domain whose latest entry was last seen within
  the cache window (5 minutes, as lens's `ttl_seconds = 300` today,
  `crates/lens/tests/fixtures/lens.production.toml:38`) is answered from that entry; the badge
  and the OG card read the head entry (grade, `last_seen_at`, the percentage of its stored run).
  Moka (`Cache::builder` in `crates/lens/src/state.rs`) survives only as the V1-only holder of the
  head's V1 rendering, keyed by entry id with the cache window as TTL; the V1 wire's cutover
  removes it. An incomplete run never replaces the head, so it is never a hit (SC12).
- **One run per domain at a time.** Concurrent requests for a domain join the run in flight and
  receive the same stream.
- **Throttle.** At most one fresh run per domain per minute, whatever started it; inside that
  minute a request gets the latest entry, or the run in flight. "Re-check now" bypasses the cache
  window, never the throttle.
- **A refused run (S26).** Whenever a fresh run is refused — by the throttle, the client's
  budget, the per-IP or global limit, or a full slot limiter (S18) — the request gets the latest
  entry (or "not checked yet") with one line naming the reason and when a run is possible again
  ("a run N s ago was incomplete; a new run is possible in M s", "too many checks from your
  address; try again in M s", "netray is busy; try again in M s"), and "re-check now" enables then.
  The API answers `429` with `Retry-After`. An incomplete run is never served again (SC12).
- **Prerender.** A request whose `Sec-Purpose` holds the token `prefetch` or `prerender`
  (`netray_common::prefetch::is_prefetch`: tokens separated by `;` or `,`, compared
  case-insensitive, so `prefetch;prerender` counts and `prefetching` or `none` do not) never
  starts a run (S8). A cache hit or the run in flight still answers it; otherwise `admit` answers
  `NotStarted`: lens's `/api/check` answers `503 PREFETCH_REFUSED` with `Cache-Control: no-store`,
  badge and OG answer the head entry with the short Cache-Control, or `?`. It spends no budget
  token and starts no throttle minute.
- **Admission (S18).** A fresh run also needs the client's hourly budget across domains, today's
  per-IP and global limits and a slot in the domain-run limiter (P13). Start values (S33): budget
  30 fresh runs per client per hour (burst 30), per-IP 10/min burst 3, global 100/min burst 20, 8
  slots; until `netray.toml` (S10) they are lens config keys, `[admission] client_budget_per_hour`
  and `domain_run_slots` and `[rate_limit]`, re-set after V2 from 30 days of measurement. A budget
  of 0 is valid and refuses every budgeted run (retry after 3600 s). The path is
  `crates/lens/src/admission.rs`: `check_limits` (per-IP, global) and `admit` (join, prefetch
  rule, throttle, slot, then the budget for visit, re-check and API runs or the badge recompute
  limiter for badge and OG, start). lens's
  `/api/check` runs validate, `check_limits` (hits keep spending them), the cache hit, then
  `admit`; badge and OG run validate, the cache hit, then `admit`. A refusal spends no budget
  token, holds no permit and starts no throttle minute. Refusals answer per route: `/api/check`
  `429 RATE_LIMITED` with `Retry-After` (a full slot limiter: 1 s); badge and OG render the head
  entry with the short Cache-Control, or `?`. Badge and OG runs never spend the budget (image
  proxies share one address). A run with `dkim_selectors` is never a hit and never joined; it
  needs the limits, the throttle, a slot and a budget token, and starts the domain's throttle
  minute. The result page and API v1 start one through `DomainRuns::start_with` with a non-empty
  list (lens: `admit_dkim`); a prefetch starts none, and its answer is `recorded: not_stored`. The
  list is comma-separated, 1-5 selectors of 1-63 `[A-Za-z0-9-]`, empty meaning none
  (`netray_web::selectors`, spec v2-dkim-legacy-urls).

### 4.5 Retention (R11)

An hourly sweep in one transaction:

1. A domain whose latest entry's `last_seen_at` is older than 90 days is deleted with all its
   entries.
2. Otherwise an entry whose `last_seen_at` is older than 90 days is deleted, unless it is the
   latest entry or the latest entry's predecessor.

An entry whose predecessor is deleted keeps its stored diff; its `predecessor_id` becomes NULL
(`ON DELETE SET NULL`).

### 4.6 `/r/<id>` (R15)

`/r/<id>` is one entry: its result page, its evidence views (`/r/<id>/tls`, R27) and its own OG
card. It is immutable and lives as long as the entry. After the sweep it answers `410 Gone` with
a page that says the entry has expired and offers the input of the idle page; it cannot name the
domain, because nothing maps a swept ID to a domain (§4.5 deletes every row, §4.7 promises it).
V1 snapshot IDs, whose store is removed at the cutover (S2), answer the same `410`.

Until V5.6 `/r/<id>` looks up the history first, then the V1 snapshots (a lookup lens hands
to `netray-web`); a well-formed ID in neither answers `410`, a malformed ID `404`. Until V4.5 an
entry renders the minimal page of v2-entries, served by `netray-web`'s router, which lens mounts
until V5.1. Its OG card keeps the V1 layout's text lines, grade, domain and recording time, with no score,
and draws above them the plate of `spectrum::layout` (V4.4) for the entry's run over its
predecessor's (a swept predecessor leaves no fixed line): 1104 px wide, 56 px high, labels in
JetBrains Mono. `v2-result-page` builds it; `/og/<domain>.png` draws the head entry's plate when it shows the head
entry, and a plain card after an admitted run (an admitted run is no entry yet).

### 4.7 Privacy (R16)

The privacy page states: the history stores the domain, the check results and their evidence, and
nothing about the visitor; an entry lives 90 days after it was last seen, the latest entry keeps
its predecessor, and a domain nobody checks for 90 days is deleted. Rate limiters and the throttle
are in memory only and keyed by address or domain; nothing of them is written to disk. A shared
inspector result is kept in memory for one hour under a random key; a lookup of the visitor's own
address is never kept. The line
"What's stored long-term (nothing per request; aggregates only)." of
the privacy SDD (private) is replaced for the history.

The page is served by `netray-web` at `/privacy`; lens mounts it until V5.1.

## 5. Result page (R17–R26)

First level: routes, how a visit becomes a run, the streaming protocol, and the spectrum and trace
as one Rust layout. Visual reference: the design canvas rows "D3 ·" (`F.dc.html` with `trace`,
`FFirst.dc.html`, `M.dc.html`).

### 5.1 Routes

Reserved paths match first: the segments `r`, `api`, `guide`, `status`, `compare`, `inspect`,
`privacy`, `static`, the prefix `/.well-known/`, and the root files `robots.txt`, `sitemap.xml`,
`favicon.svg`, `favicon.ico`. RFC 9309 fixes `robots.txt` at the root and RFC 8615 defines
`/.well-known/`; `site/` serves `robots.txt`, `sitemap.xml` and `favicon.svg` today, and
`crates/netray/src/site.rs:17` serves `/.well-known/mta-sts.txt`; `favicon.ico` is reserved
because browsers fetch it when a page declares no icon (WHATWG HTML Standard, `rel=icon`). After them, a first path segment containing a dot is a domain. A test asserts
that every reserved path answers its own route, never a result page.

| Route | Method | Answer |
|---|---|---|
| `/` | GET | idle page (R23) |
| `/<domain>` | GET | the result page (§5.2) |
| `/<domain>/run` | POST | starts or joins a run; answers the SSE stream of fragments (§5.3) |
| `/<domain>/<protocol>` | GET | evidence view of the latest entry (R27, §6) |
| `/<domain>/history` | GET | the history as a table (R25) |
| `/r/<id>`, `/r/<id>/<protocol>` | GET | an entry and its evidence views (R15, R27) |
| `/r/<id>/og.png`, `/og/<domain>.png`, `/badge/<domain>.svg` | GET | OG card and badge from the stored entry |

Starting a run is a POST, never a GET (P06): a crawler, a link preview or a prerender (S8) can
read every page and start nothing.

Until `v2-cutover`, the result routes (`/`, `/<domain>`, `/<domain>/run`, `/<domain>/history`)
mount on lens's router when its history store is enabled (`netray_web::pages::result::router`, merged in `crates/lens/src/lib.rs`; without history lens's `/` stays the SPA).

### 5.2 A visit

1. `GET /<domain>` renders the latest stored entry as full HTML, server-side: crawlable, and
   complete on first paint.
2. If that entry was last seen within the cache window (S17), the page is final; "re-check now"
   posts to `/<domain>/run`.
3. If it is older, or there is none, the streaming island posts on load to
   `/<domain>/run`, so a visitor with a browser sees a fresh run unless admission refuses it (§4.4, S26),
   as lens does today (`crates/lens/frontend/src/App.tsx:64` starts a check on load). A
   client without JavaScript keeps the stored entry, or "not checked yet" with a check button.
   That load post carries `trigger=visit`; a fresh visit starts nothing.
4. During the run the stored entry's spectrum stays visible, dimmed, until the first section
   replaces its band; grade and diff appear only at the end (R22).

### 5.3 Streaming (R22, S7)

`POST /<domain>/run` answers one SSE stream of `fragment` events (an element ID and its HTML), every
fragment rendered by the same templates as the full page:

| When | Patched elements |
|---|---|
| start | run line ("running"), progress ray: five segments, all pending |
| each section finishes | its ray segment; its band of the spectrum; the open issues block as known so far; its evidence tab |
| section times out or errors | its ray segment marked incomplete; its band shown as unmeasured |
| end | header (grade or `incomplete`), run line, the full spectrum with fixed marks and labels, the trace, the diff block (or R19's line), the passed-checks block |

A request that joins a run in flight (§4.4) first receives the fragments of the sections already
finished, then the live ones. The stream ends with the run; a disconnect does not cancel a run
that others may have joined.

### 5.4 Spectrum (R24, R26; S7, S16)

One pure Rust function, `spectrum::layout(current, older, catalogue, width)` in
`netray_web::spectrum` (`crates/web/src/spectrum.rs`), yields the geometry. It takes each run as
its per-check statuses (`CheckId` → `Status`), its per-section states (`SectionState`:
`Measured`, `NotApplicable`, `Unmeasured`) and the profile it was scored with (§3.8), `older`
newest first; a caller maps its stored entries onto statuses with profiles (`v2-result-page` for
the page, `/r/` and the OG cards; `v2-inspectors` for a live run). One template renders it as
inline SVG on every page, and the OG card renders the same geometry with resvg (P26).

- **x:** one line per check of the catalogue, grouped by protocol in the order DNS, TLS, HTTP,
  email, IP, and by catalogue order inside a group; a hairline marks each group boundary; group
  names sit on the axis below the plate, centred under their region, each followed by the
  section's letter grade (the section percentage of `score_run` through the profile's thresholds;
  a section without a score shows its name only). The 32 px axis carries one tick per line
  boundary (N + 1), 4 px, and 10 px at the plate's ends and at region bounds.
- **Height:** a measured line is `plate × (0.35 + 0.65 × w / w_max)` high, `w` the check's
  effective weight in the grade (§3.9) and `w_max` the largest in the run: the heaviest line fills
  the plate (92 px, 80 px at phone width, `crates/web/tokens.json` `spectrum`; 56 px on the OG
  card), the lightest is at least 35 % of it, and the order by weight holds. Muted lines take the
  smallest measured height.
- **Inspector band:** an inspector draws its protocol's lines as the slim spectrum of board G:
  the plate alone, 96 px (`spectrum.bandPlateHeight`) with two guide rules at a third and two
  thirds, no label band and no axis or group name; the inspector names each line and its code
  under the plate (v2-http-ui requirement 14).
  A TLS run over several ports (v2-tls-ui) has no band under the h1: a tab row (the `tabs`
  island, the band port's tab current) holds one panel per port in input order, each with that
  port's own band and check list (`inspect-band-<n>`, `inspect-checks-<n>`) and its port view;
  a tab names the port, " · STARTTLS" when its handshake holds `starttls`, and its worst status
  as a tone with "<f> fail · <w> warn" when a line fails or warns. Without JavaScript every panel
  shows, in order. A one-port run keeps the band under the h1; the shared run renders the same.
  The OG card keeps the page's line geometry and fixed-line drawing at 1104 px and 56 px, without
  the axis group names.
- **State:** pass 2 px, warn 3 px, fail 4 px in the status mark colours; fixed since the previous
  entry is a hollow 5 px line with a ring (R24); not applicable, not tested and unmeasured get the
  muted mark of R42, so no line is missing.
- **Labels:** every warn, fail and fixed line carries its short name (a new catalogue field
  `short`, at most 8 characters) above the plate, on a leader. Placement in §5.5.
- **Width:** the pitch is the container width over the line count; below `linePitchMin` (8 px)
  the plate keeps 8 px per line and scrolls sideways (R26). With 57 checks this happens at phone
  width (358 px of content gives 6.3 px).

### 5.5 Label placement (open question of the handoff)

The canvas staggers leaders by label index (`n % 3`: 8, 22, 36 px), which separates DKIM and
DMARC only by luck of their index. The layout places labels by measured width instead:

1. Labels are monospace, so a label's width is known without a font: characters × 0.62 em (SF Mono,
   which `ui-monospace` resolves to on macOS, advances 0.618 em, Menlo 0.602 em: the `hmtx`
   advance over `unitsPerEm`, 1266/2048 and 1233/2048, read from `/System/Library/Fonts`),
   measured at `font.size.caption` 11 px, the size the labels draw at, plus 4 px padding.
2. Labels are taken in line order, which is x order; each goes into the lowest row (shortest
   leader) where its interval overlaps no label already placed there. A box is left-aligned at
   its leader: it spans [x, x + w), the padding between leader and text. Intervals are
   half-open, so boxes that only touch do not overlap. A box that would pass the plate's right
   edge shifts inward to end at the edge; its leader stays on the line. A box wider than the plate
   starts at 0. The placement is made once, at the narrowest plate; at a wider plate a box sits
   at max(0, min(its scaled leader, plate − w)) (`spectrum::scaled_start`), so a shifted box
   stays over its leader and no row gains an overlap.
3. There are at least three rows; when no row is free, a row is added above (S20). The label band
   grows in height, never the plate in width, so R26 holds: the plate scrolls only below the
   minimum pitch. Nothing is dropped: every warn, fail and fixed line keeps its label (R24). Four
   adjacent failing lines at 8 px pitch with 4-character labels at `font.size.caption` 11 px (31.3 px each, 24 px apart per row) need a
   fourth row.
   A label in row r sits `spectrum.labelLeader` + r × `spectrum.labelRow` above the plate (8 px
   and 14 px: the canvas's 8, 22 and 36 px stagger), and its leader is as tall (6, 18 and 30 px at phone width through the phone tokens). The label band is
   `spectrum.labelBand` (56 px, 46 px at phone width) while at most three rows are needed and one `spectrum.labelRow` more for each row beyond
   the third, where rows is the largest row count of any run, so switching runs never changes
   its height.
4. Replay (§5.6) needs the labels of every shown run: the layout computes them for each run
   server-side, and the `spectrum` component renders every run's state, so the island only
   switches states and the placement exists once, in Rust. The plate holds one
   `<g id="band-<protocol>" data-protocol="<protocol>">` per protocol in protocol order. Each band
   holds one `<g class="spectrum__run" data-run="<k>">` per run (k = 0 the current run, then newest
   first), and the label band holds one `<div class="spectrum__labels" data-run="<k>">` per run.
   Only the shown run's groups and label set carry `data-shown`, and the island moves that
   attribute only. A run group carries `data-unmeasured` when that run's section is unmeasured
   (§5.3, Rule M); a not-applicable section does not, and its lines stay muted either way.

### 5.6 Trace and replay (R25, R26)

- Under each line a column of runs, newest on top, one row per stored entry: 5 px (6 px at phone
  width); pass is a hairline in the pass hairline colour (3:1, R42), warn and fail a block in their
  colour, not tested and not applicable the muted mark. Incomplete runs are never stored, so never
  in the trace.
- The trace shows the latest 24 entries; the history table (`/<domain>/history`) holds all of
  them (R25).
- Desktop: hovering a row enlarges it, shows its date and grade in the right gutter and replays
  the spectrum in that run's state; hovering a line gives its history in one sentence ("warn
  09-19 to 09-24 · pass since 10-08"); a click pins the run, a second click releases it. The pinned
  or replayed run carries the marker (R43).
- Phone width: a run stepper (‹ ›, 44 px targets) replaces hover and replays; tapping a line (a
  full-height target per line) shows its history sentence.
- The island holds three values (hovered run, pinned run, selected line) and switches data
  attributes; it computes no layout.

### 5.7 Page order and states (R18, R19, R23)

Header (grade with score and descriptor, run title, domain, re-check now, share) → hard-fail
banner, when a hard-fail check failed or a section was left out of the score → spectrum with trace
and legend → since run k−1 (h2) → open issues (§5.8, h2 "<n> lines need attention") → evidence
(§6, h2 "Evidence") → passed checks, collapsed in a `<details>`. The run title reads "Run k ·
date UTC · c checks · profile v", then the duration when stored, "cached" when the page answered
from a fresh entry and "first run" on the domain's first entry. The score and the banner are
derived at render time with `score_run` under the entry's profile version; the score is hidden when
its grade differs from the stored grade, and so is the banner's hard-fail sentence. `k` is the entry's position among the domain's stored entries, oldest first: the retention sweep (§4.5) renumbers the entries it keeps.

- First entry: the diff block reads "first state recorded — re-check after your change" (R19).
- Incomplete run: grade `incomplete` (F when a hard fail failed, S35), finished sections shown, diff against the last entry
  marked incomplete; without one, "not recorded: this run is incomplete" (R19).
- Idle (`/`, R23): input; recent domains with last grade and date from browser storage (an
  island; nothing is sent until the visitor re-checks); examples; one sentence of scope; the way
  to the inspectors.

### 5.8 Open issues (R20, R21)

Every warn and fail appears once, as its catalogue sentence with `fix_hint`, a link to its
evidence in the same run and to its guide. Grouped by `fix_owner` by default, switchable to
severity or protocol; severity orders within a group (R21), fail before warn among equal severity. The grouping choice lives
in browser storage; the server renders the default and the island re-groups in place from data
attributes, without a request.

## 6. Evidence views and inspectors (R27–R31)

### 6.1 Evidence views (R27–R30)

- **Routes** (§5.1): `/<domain>/<protocol>` shows the latest entry, `/r/<id>/<protocol>` entry
  `<id>`, which never changes. The incomplete run's evidence exists only on its own result page,
  as tabs filled by the stream; it is never reachable by URL (R27). Every view names its run:
  "run of <created_at as YYYY-MM-DD HH:MM> UTC · entry <id>" (the creating run, not the one that
  last saw the entry), or "incomplete, not recorded".
- **Order** (R28): the protocol's checks first, as check rows; the evidence blocks below, each
  rendered by the one evidence block component per shape (S15). A check row links to the blocks it
  references; a block lists the checks that reference it ("feeds: TLS chain trusted, TLS not
  expired"). Values show for people (durations in ms, s or min and s, booleans as yes or no,
  times to the minute in UTC inside a `time` element, a repeated key `<key>#<n>` as `<key>` with
  the full key in `data-key`); the exports keep the stored keys and values.
- **Protocol views** (v2-http-ui): `crates/web/src/pages/views/` holds one module per protocol and
  one entry function that every renderer (evidence views, inspector parts, the result page's live
  "All evidence" details) asks per block, in the run's block order, with the run's check statuses,
  the value decoration, the block's feeds and the sibling blocks shown with it (the inspector
  part's blocks; the run's blocks of the block's protocol in the evidence view and the live
  details). A view claims a block only when it renders every key the block holds, and renders it
  as a `section` with the anchor `ev-<block id>` and the block's feeds line; an unclaimed block
  renders through the generic evidence block, which stays free of module names. One view may
  render several blocks in one fragment (v2-tls-ui: the TLS port view renders a whole port at its
  `tls.addresses` block): whether a block is taken is one pure function of the siblings, the
  fragment carries an anchor `ev-<block id>` for every block it took, and each taken block answers
  with an empty fragment, so it appears once. In the inspector a part that carries its own checks (each TLS port's, v2-tls-ui) renders its
  views with them when it arrives and is not streamed again; for any other part the checks arrive
  with the band, after the parts, and a part holding a claimed block is streamed again after the
  band, its views then carrying the check tones.
- **Part views** (v2-dns-ui): `pages::views::render_part` is asked once per inspector part,
  before its blocks. The DNS part view reads `dns.answers` and claims it, `dns.servers`,
  `dns.warnings` and each job block whose every value its fragment shows (a `dns.<type>` records
  block whose every record data is among that type's answers, a "not measured" fields block whose
  type has a card, a `dns.compare` or `dns.authcompare` table whose every record is among its
  type's answers). The fragment renders in place of the first claimed block, carries
  `ev-<block id>` for each claimed block, and the other claimed blocks are skipped; unclaimed
  blocks (`dns.errors`, Rule M) render as before. Bar lengths and card ranks are computed in Rust.
- **Shared evidence** (R29): a block is shown in its owner module's view only; another view
  shows a one-line reference that links there (`tls.caa_compliant` → the CAA block in the DNS view).
- **Explore live** (R30): every view links to the inspector with prefilled parameters; the link is
  derived from the block, not written per view. Every block carries the anchor `ev-<block id>`,
  which check rows and the result page's evidence links target. One function derives the links from
  the block: each link is apex-relative, `/inspect/<tool>?…`, valid before and after the cutover,
  with percent-encoded values. A block with a per-row rule (`tls.addresses`, `email.mx`,
  `ip.addresses`) gets one link per row, a block with a per-block rule (`dns.<type>`,
  `email.dmarc`, `email.mta_sts`) one link, and the view one link of its own; other blocks get none:

| View | Explore live |
|---|---|
| DNS | DNS inspector: the domain with the parser's default types (it blocks `ANY`, `AXFR` and `IXFR`); a `dns.<type>` block → that name and type |
| TLS | TLS inspector: `<domain>:443`; an address block → that address |
| HTTP | HTTP inspector: `https://<domain>/` |
| Email | DNS inspector for a policy record (`_dmarc.<domain>` TXT, `_mta-sts.<domain>` TXT); TLS inspector on an MX host, port 25, STARTTLS (SMTP STARTTLS is chosen by port, `crates/tls/src/tls/connect.rs:91`) |
| IP | IP inspector for each address |

### 6.2 Inspectors (R31; S3)

Inspectors are jobs without a domain verdict. Each is a page on its subdomain (email has none, S3) and the same page
under `/inspect/<tool>` on the apex (R33); the job runs through the module crate's inspector
function (§3.1), streams like a run (S25) and is never stored in the history. Before v2-cutover the inspectors
exist only under `/inspect/<tool>`, on netray-web's router merged into lens ahead of the SPA
handler; the subdomains keep the V1 SPAs.

| Inspector | Jobs | Band (R31) |
|---|---|---|
| DNS (`dns.`) | query (any name, types, resolver), trace, resolver compare, authoritative compare, DNSSEC chain | the DNS band of the queried name's registrable domain (Public Suffix List), checked live with the DNS checks for every job (S29) |
| TLS (`tls.`) | any host and port, STARTTLS for SMTP as today; IMAP and FTP are stubs today (`crates/tls/src/tls/connect.rs:201`) and are not offered | the TLS band of that endpoint (port 443, else the lowest port); one evidence part per inspected port |
| HTTP (`http.`) | any URL, path included | the HTTP band of that URL |
| Email | a domain, then DKIM selectors separated by spaces or commas; the job behind `POST /api/v1/email/inspect`, sharing its `[api.email]` limiter and slots | the Email band of that domain |
| IP (`ip.`) | the caller's address, any address; `GET /inspect/ip` with neither `ip` nor `r` renders the caller's run server-side under the `[api.ip]` admission and the IP deadline (`Cache-Control: private, no-store`; a refusal, an unavailable lookup or the deadline is a notice under the address; a prefetch gets `503`), `?ip=` keeps autostart, and a run of a given address links "Show my address" | the IP band (reputation) of that address |

- Each run is marked "live · <date> UTC · not recorded" and carries no grade; the back link shows the domain's latest stored grade, read by the route and never written.
- **Job route.** `POST /inspect/<tool>/run` answers an SSE stream of `fragment` events, then `end`.
  Invalid input is one fragment; a refusal by a limiter is `429` with `Retry-After`; a prefetch
  starts nothing and gets `503` with `Cache-Control: no-store`.
- **Limits.** `[inspect.<tool>] deadline_ms, max_concurrent` per inspector, beside the
  `[api.<tool>]` limiters, which the page route shares with `/api/v1`. Defaults: deadline DNS
  30 000, TLS 15 000, HTTP 30 000, Email 35 000 (past the email inspection's own 30 s cap) and IP 5 000 ms; 8 slots each.
- **Band.** `spectrum::layout` over `Catalogue::for_protocol(<protocol>)` with the one live run
  under `Profiles::current()`. On the page, DNS `+check` is not a job: the band covers it; API v1 runs the DNS checks alone at `/api/v1/dns/check` (v2-dns-api). The DNS band is
  that of the queried name's registrable domain, run under the job's admission with no limiter of
  its own: the stream never refuses.
- **Rule M.** A DNS lookup that failed shows "not measured" with its reason, per record type and
  beside the answered ones; an inspector part is never empty.
- When the target is a domain (or its apex), the page links back to `netray.info/<domain>`.
- **Sharing.** A finished run is kept in memory as data for one hour under a random 12-hex key,
  at most 1 000 runs, the least recently used dropped first. `GET /inspect/<tool>?r=<key>` renders it
  server-side as "shared · <date> UTC · not recorded" and starts no job; a malformed, expired or
  foreign key answers `404` with the idle shell and a notice. A DNS run also writes its result to
  API v1's DNS result cache under the same key, and `/inspect/dns?r=` opens a key only that cache
  holds. The caller's own address, posted or rendered by `GET /inspect/ip`, has no share key and is never kept.
- Every inspector job has its own deadline (P12) and its own concurrency limit (P13); a job's
  outbound fetches go through `netray_common::fetch` (P18).

## 7. URLs and API (R32–R35)

### 7.1 Apex API v1 (R34)

One versioned API under `netray.info/api/v1`, JSON, its OpenAPI document at
`/api/v1/openapi.json`, its errors in the format of `specs/rules/architecture-rules.md` (monorepo).
The API serves the stored structures (§3.5, §3.7, §4.1) as they are; it computes no verdict (R5).

| Endpoint | Answer |
|---|---|
| `GET /domains/{domain}` | the latest entry `{id, domain, created_at, last_seen_at, predecessor_id, profile_version, grade, engine_version, run}` (Unix seconds; `run` as stored, its checks' `findings` and `evidence` included; no fingerprint, no diff); `400 DOMAIN_INVALID`, `404` when none, `503` with the history off |
| `POST /domains/{domain}/runs` | a fresh run under the throttle and admission (§4.4, S18), joining one in flight; `?dkim_selectors=a,b` runs those DKIM selectors in a run that never joins, is never joined and is not recorded (§4.4), an invalid list `400 INVALID_INPUT`; with `Accept: text/event-stream` one `section` event per section (`{protocol, outcome, reason, checks, blocks}`) as it finishes, then one `done` event carrying the answer; otherwise the answer `{recorded, entry_id, run, diff}`, `recorded` being `first`, `identical`, `changed` or `not_stored`; `429` with `Retry-After` (`THROTTLED`, `BUDGET_EXHAUSTED`, `RATE_LIMITED`, `BUSY`); `503 PREFETCH_REFUSED` for a prefetch that joins nothing |
| `GET /domains/{domain}/diff` | `{entry_id, predecessor_id, diff}`: the latest entry's stored diff, both `null` for a first entry |

| `GET /entries/{id}`, `GET /entries/{id}/diff` | one entry (`/r/<id>`) in the shapes above; `410` for a well-formed ID without an entry (swept, or a V1 snapshot), `404` for a malformed one |
| `POST /dns/query`, `/dns/trace`, `/dns/compare`, `/dns/authcompare`, `/dns/dnssec` | DNS inspector jobs on prism's bodies (`{domain, record_types, servers, transport, dnssec}`; trace `{domain, record_type, timeout_secs}`; dnssec `{domain, timeout_secs}`); with `Accept: text/event-stream` prism's named events (`batch`, `error`, `enrichment`, `done`; trace `hop`, dnssec `chain`), otherwise one object collecting them: `{batches, errors, enrichment, done}`, trace `{hops, errors, enrichment, done}`, dnssec `{levels, errors, done}`, with `done` `null` after the 30 s stream deadline |
| `GET /dns/query`, `/dns/compare`, `/dns/authcompare`, `/dns/trace`, `/dns/dnssec` with `q` | the same jobs on prism's query language (`domain [TYPE...] [@server...] [+flag...]`, `netray_dns::parser::parse`); trace takes the first type, dnssec the domain; in `GET /dns/query` a routing flag (`+trace`, `+compare`, `+auth`, `+check`) answers `307` to that job's path with the same `q`; `+dnssec` adds DNSKEY and DS (v2-dns-api) |
| DNS job results | query, compare and authcompare collect a `summary`: per record type every server's answer (outcome, records with TTL and presentation data, SOA serial age, transport, response time) and its agreement (`agree`, `diverge`, `single`, `unmeasured`, Rule M), per server the lookups and median response time; the stream sends it as a `summary` event before `done`. Every job's `done` carries a `cache_key` (v2-dns-api) |
| `GET /dns/results/{key}` | `{key, mode, query, result}`: a DNS job's collected result (or a check) for an hour after it finished, 1 000 at most; `400` for a malformed key, `404` when unknown or expired |
| `POST /dns/check`, `GET /dns/check` with `q` | the DNS module alone on one domain, live, not stored: `{protocol, outcome, reason, checks, blocks, cache_key}`, JSON only; an address or a malformed name is `400` |
| `POST /dns/parse`, `GET /dns/servers`, `GET /dns/record-types` | the query language without running it (`{tokens, completions, query, error}`), the resolver catalogue (`{providers, groups}`) and the record types (`{record_types}`), behind the `[api]` per-IP limiter |
| `POST /tls/inspect` | `{host, port}` or `{host, ports}` (one to `limits.max_ports` ports, each inspected once; both together, an empty list or port 0 answer 400), `port` 443 by default; the port chooses STARTTLS as tlsight does (SMTP on 25 and 587, IMAP on 143, FTP on 21); there is no `starttls` field (it can come later as an additive property) |
| `POST /http/inspect` | `{url}` |
| `POST /email/inspect` | `{domain, dkim_selectors?}` (`dkim_selectors` an array of at most `dkim.max_user_selectors` selectors, default 5): the email module alone, live, not stored (R34 names email; the UI is the `/inspect/email` page, S3); with `Accept: text/event-stream` beacon's events (`category` per category, one `evidence`, `summary`, typed by their `type` field), otherwise `{categories, evidence, summary}` |
| `GET /ip`, `GET /ip/{address}` | the caller's address, or any global address, with enrichment (S40); `?field=<name>` answers that field as `text/plain`: `ip`, `asn`, `country`, `city`, `region`, `timezone`, `latitude`, `longitude`, `isp`, `location`, `network`, `host`, `cidr` on both, `tcp`, `user_agent`, `headers`, `all` on `/ip` only; `?format=json`, `yaml`, `toml`, `csv` or `plain` renders the answer or the field in that form, and without it an `Accept` naming YAML, TOML or CSV picks that form; `?fields=a,b` keeps those top-level keys of a structured answer; `?lang=<tag>` adds localised place names; an address gets reverse DNS unless `?dns=` is other than `true` or `1`; `/ip?ip=X` answers for X, with `tcp` and `user_agent` refused and `headers` and `all` answered; plain `headers`, `cidr` and `ip` answer with the IP module off |

| `GET /catalogue`, `GET /profiles/{n}`, `GET /meta` | the check catalogue `{checks}`, a profile `{name, version, sections, thresholds}`, and `{version, api, current_profile, profiles, evidence_schema_version, limits, attribution}`, `attribution` being the MaxMind GeoLite2 notice the ip data requires |

Every non-2xx answer is `{"error": {"code", "message"}}` with a stable code: `DOMAIN_INVALID`,
`INVALID_INPUT`, `BATCH_TOO_MANY` (400), `TARGET_BLOCKED` (403), `NOT_FOUND` (404),
`METHOD_NOT_ALLOWED` (405), `GONE` (410), `PAYLOAD_TOO_LARGE` (413), `RATE_LIMITED`, `THROTTLED`,
`BUDGET_EXHAUSTED`, `BUSY` (429, with `Retry-After`), `INTERNAL_ERROR` (500), `UNAVAILABLE`,
`PREFETCH_REFUSED` (503). A request whose cost exceeds a limiter's burst, which no wait can
admit, is `400 INVALID_INPUT` naming the cost and the limit; `429` is only for a request that passes
after `Retry-After` (v2-input-edges). The interactive docs page is `/api/v1/docs`.

Within `v1`, changes are additive only; a removal or change of meaning is `v2`, served beside `v1`
until `v1` is retired (P33 for the API's own future, after the one hard cut of R35).

### 7.2 `ip.netray.info` (R34, R35)

`curl ip.netray.info` keeps answering the caller's address as plain text, chosen by the
user-agent negotiation that exists today (`crates/ifconfig-rs/src/negotiate.rs:29`). In a browser
the same URL is the IP inspector. Every function behind the other routes of `ip.` today moves
into `/api/v1` (S23); the routes themselves (`/json`, `/yaml`, `/toml`, `/csv`, `/all`, `/asn`,
`/network`, `/range`, `/ip/cidr`, `/batch`, `/diff`, `/ip/{fmt}`, `/ipv4`, `/ipv6`, `/meta`,
`/docs`, `/api-docs/openapi.json` and the `/{field}/{fmt}` family) are cut (R35) and answer `410` naming their `/api/v1` successor. S40 brings back the field and format routes (`/json`, `/yaml`, `/toml`, `/csv`, `/all`, `/ip/cidr`, `/asn` without a number, each field and `/{field}/{fmt}`), and the root's `Accept` negotiation and `?ip=`: `netray_web::api::ip_host` serves them ahead of the `410` table; the rest stay cut.

### 8.4 Islands (S7, S22, S25)

| Island | Does |
|---|---|
| `theme` | cycles auto, light and dark; remembers the choice in browser storage |
| `status` | fills the status page's monitor list and event feed from the uptime provider |
| `stream` | posts a run or an inspector job, reads the SSE stream, replaces elements by ID (S25) |
| `spectrum` | hover, pin, run stepper, line history sentence; switches precomputed states (§5.6) |
| `issues` | regroups open issues from data attributes; remembers the choice (R21) |
| `recent` | recent domains with last grade and date in browser storage (R23) |
| `dns` | the DNS inspector's query builder (S22) |

The `stream` wire has two events. `fragment` carries the JSON `{id, html}` and replaces the
element with that ID; `end` carries `{}` and closes the stream. The island applies the events
whatever the HTTP status, when the content type is `text/event-stream`, and in arrival order. The
server replays the finished sections to a client that joins a running job (§5.3), so a joiner
needs no separate client path. The island mounts on a `<form data-island="stream">` (it reads
the form's `FormData`). The form carries `data-stream-url`, `data-stream-autostart` and
`data-stream-state` (`running`, `done` or `error`); an element with `data-stream-error` inside
that form shows the failure. The island dispatches `netray:stream-fragment`, bubbling, on each
top-level element the inserted fragment holds (it reaches the form only when the target sits
inside it, so listen on `document` or an ancestor of the target), and `netray:stream-end` on the
form.

Islands compute no layout and hold no verdict; they read data attributes the server wrote. A
test caps the bundle at 30 KB gzipped (P35). Tests: vitest with happy-dom, one config, run by the
gate; the islands' tests are the only frontend unit tests. Today's 19 vitest files of the Solid
apps and `common-frontend` (run by `just test-frontend`, `npm test --workspaces`) go with them.

### 8.5 The gate (R45, P35)

A `cargo test` in `netray-web`, part of `just adlc-verify`, fails when:

1. a template, stylesheet or island outside `tokens.css` contains a colour literal (hex, `rgb()`,
   `hsl()`, a named colour), a `border-radius`, `font-family`, `font-size`, `stroke-width` or
   border width that is not a `var(--…)` of its own token family (a radius only `--radius-*`;
   operator, 2026-10-15);
2. a class name of an R44 component is defined in a stylesheet other than the component's own,
   or a template renders a component's markup without its macro;
3. an inline `<script>` other than the speculation rules or an `application/ld+json` data block
   appears in a template; the speculation rules are the only inline executable script (S25).

It replaces the hand-kept tracker `frontend-rules-compliance.md` (private),
which is retired when the gate lands.
