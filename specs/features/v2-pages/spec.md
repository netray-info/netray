# Spec: v2-pages

Status: Ready for Implementation
Created: 2026-10-17

## Goal

`netray-web` serves the V2 static pages through `netray_web::pages::router()`: every guide, the guide index, compare (its netray column generated from `netray_engine::catalogue()`), status, and the 404 and 500 pages, all askama templates on one `templates/base.html`. Every response carries a CSP whose `script-src` has neither `'unsafe-inline'` nor `'unsafe-eval'`, only `'self'` and the generated hash of the only executable inline script, the speculation rules; `application/ld+json` data blocks are allowed and are not executable. Those rules prerender only `/guide/*` and `/r/*`. View transitions run only under `prefers-reduced-motion: no-preference`. An esbuild islands bundle holds the shared `stream` island (S25) and the `theme` and `status` islands, stays under 30 KB gzipped, and its type check and vitest suite run in `just adlc-verify`. `specs/rules/frontend-rules.md` describes V2. A repo check and a render test find no codename in templates, static files, islands, compare data or rendered pages. The four items Phase 4a deferred to the pages phase are closed. lens mounts the router ahead of its SPA fallback (X1), so `acceptance-local` and the screenshots reach the pages; nothing ships before the single 0.30.0 release, and production keeps routing `/guide`, `/compare` and `/status` to `netray site`. This is SDD V4.8–V4.12, scoped to these pages.

## Non-goals

- No route of the result page, evidence views, history table, inspectors or idle page (V4.4–V4.7, V4.13). `GET /` without `?d=` is not answered here.
- No `/r/<id>`, no 410 page, no `/privacy` route and no privacy text (V2.7–V2.8, `v2-entries`, which owns `/privacy` and §4.7's text).
- No API v1, no API field, no export (Phase 3). V4.12's API half belongs to the API lane.
- No `netray serve`, no apex router and no host routing (V5.1, v2-cutover). The router reaches the binary only through lens's merge (requirement 33).
- No deletion of `site/`, `netray site`, `tests/repo/test_site.sh`, `validate-site`, `check-sitemap`, `site/scripts/build-sitemap.mjs` or `COPY site` in the `Dockerfile`. All of them go with `netray site` in v2-cutover (decision log).
- No port of `site/tools/index.html` or `site/api/*.html` (V1 tool list and V1 API docs; their URLs are v2-cutover's redirect map, SDD §7.3).
- No root files at the apex beyond `/robots.txt` and `/sitemap.xml` (no `/.well-known/mta-sts.txt`, no `/bimi-logo.svg`, no `/favicon.ico`): §5.1's reserved-path test needs the apex router, which v2-cutover builds.
- No `spectrum`, `issues`, `recent` or `dns` island (§8.4; they come with the pages that use them). No stream route: the routes that answer `fragment` streams (`POST /<domain>/run`, `POST /inspect/<tool>/run`) are v2-result-page's and v2-inspectors'; this feature builds the island and the shared wire encoder they use.
- No re-check of guide content against catalogue or profile v3, the scoring guide included (Out of scope).
- No change to the Solid frontends, `packages/common-frontend` or their vitest files (deleted in V5.1).

3. The gate reads an unquoted attribute value that is an askama expression (`{{ … }}`, `{% … %}`, `{# … #}`) as one opaque value ending where the expression ends. An unquoted value is either plain text or exactly one `{{ … }}` or `{% include … %}` span followed by whitespace, `>` or `/>`; rule 3 refuses any other askama span starting, inside or glued to an unquoted value (control flow and comments go inside a quoted value). Because such a span may render empty, a tag holding one is also read as the gate read it before this feature (every span blanked, the next token being the value), and the gate reports what either reading breaks. Inside a quoted value, `javascript:` is refused anywhere in an `href`, `src` or `action`, and a `type` holding an askama span never counts as `speculationrules`. The next attribute is then parsed as its own attribute: `<button class={{ c }} onclick="go()">` and `<script src={{ asset }} onload="init()"></script>` fail rule 3 on the handler, and `<script src={{ asset }} defer></script>` still passes. Each case is a planted row.

28. The `stream` island (S25, X3) mounts on a `<form data-island="stream">`. It posts the form's fields, URL-encoded, to the form's `data-stream-url` (else its `action`) with `fetch`, method `POST`, `Accept: text/event-stream` and `credentials: "same-origin"`, adding a `trigger` field: the submitter's `value` when the submit button is named `trigger`, else the value of `data-stream-autostart`.
    - **Autostart:** when the form carries `data-stream-autostart="<trigger>"`, the island posts once on mount; while `document.prerendering` is true it waits for `prerenderingchange` and posts nothing before (S8). Without the attribute it posts only on submit. The server decides the attribute: v2-result-page writes it (`visit`) for a stale or missing entry, v2-inspectors for a prefilled input.
    - **Submit:** it intercepts the form's submit (a re-check, a new inspector query) and posts; a post while one runs aborts the running one (`AbortController`).
    - **Wire:** it parses the response body as SSE (`event:`, multi-line `data:`, blank-line dispatch, `:` comments ignored) whatever the HTTP status when the content type is `text/event-stream`, so a `429` refusal's fragment is applied too. A `fragment` event's data is JSON `{"id": string, "html": string}`: the element with that ID is replaced by the HTML parsed in that element's context (inside an `<svg>` wrapper for an SVG target, else `Range.createContextualFragment`, so an SVG band stays in the SVG namespace), with every `<script>` element removed before insertion, and `mount()` (requirement 5) runs over the inserted nodes. A fragment whose ID matches no element is dropped. An `end` event ends the stream: nothing after it is applied, and a run superseded by a new post applies nothing more.
    - **Replay for joiners:** fragments are applied in arrival order and a fragment for an ID already replaced replaces it again, so a joiner's stream (the fragments of the sections already finished, then the live ones, §5.3) needs no client-side distinction.
    - **State and hooks:** the form carries `data-stream-state` = `running` from the post, `done` after `end`, `error` on a network failure, an aborted body without `end`, or a response that is not `text/event-stream`; on `error` a server-written `[data-stream-error]` element inside the form is unhidden. It dispatches `netray:stream-fragment` (detail: the ID) on each replaced element and `netray:stream-end` on the form, both bubbling. Consumer-specific behaviour (v2-result-page's `data-refreshing`, countdown and re-check enabling) is built by the consumer on these attributes and events and keeps this requirement's tests green.
